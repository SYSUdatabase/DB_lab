## 三、逐阶段实施顺序与检查点

### P0｜冻结 v0.1 与迁移前基准（第一个闸门）

- [ ] 以 SQL Server **只读系统目录**核对源数据库实际表、PK/UK/FK、CHECK、视图、角色及权限，和 DDL 逐项比较；若与源 SQL 不一致，先停止，不进入迁移。
- [ ] 在**获得后续执行授权之后**，对源库进行安全备份并核验备份文件完整性/可还原性；使用受权限控制的临时目录，在 SQL Server **以新库名还原一份数据副本**。记录数据库名、备份标识、来源/生成时间与备份校验。不将备份放入仓库。任何还原操作先核对物理文件路径和逻辑文件名，避免覆盖已有 MDF/LDF。
- [ ] 迁移前在**同一个准备迁移的副本**上运行只读基准 SQL，保存 **订单明细、商品销售统计、库存查询** 的有序结果，并记录 14 表行数、主码集合、复合候选码重复数、空值与孤儿 FK 情况、关键视图结果及相关角色权限。
- [ ] 基准查询沿用旧销售规则：仅 `Orders.status='paid'` 参与销售统计，以 `OrderDetails.unit_price/subtotal` 的**成交快照**为准；库存仍是 `UpstreamAccount/Inventory` 的上游额度，不是商品件数。固定历史快照口径不得悄悄改成当前时钟。
- [ ] 记录迁移前的 `signature.sql` 或同等业务内容签名作为保护性证据；若新增/拆分表导致整表签名不可逐字节比对，则改为**业务键/业务结果签名**、行数说明及双向集合对账。
- **P0 通过条件**：源库原样保留；已有 v0.1 数据的副本已可独立访问；备份/恢复材料和迁移前查询基准可追溯，未写回源库。若权限/文件空间/恢复失败，暂停而非降级为删库重建。

### P1｜逐表梳理函数依赖和三类异常

- [ ] `dependency_normalization.md` 对 **全部 14 张表**设一张独立记录：单行含义、属性集合、主码、**全部候选码**、主要业务 FD（写 `X → Y` 与成立前提）、非平凡性/决定因素、是否可能有部分依赖/传递依赖、1NF/2NF/3NF 判定和原因。
- [ ] 分清约束来源：`PK/UNIQUE` 提供部分**结构保证**；其他 FD 来源于**业务规则**，必须由小组确认。样例没有重复值**不能证明 FD 成立**，独立 `IDENTITY PK` 也不能消除别的字段之间的依赖。
- [ ] 对每张表列出**插入、修改、删除**三种异常：若不存在，也要说明具体机制如何避免，而不是留空。数据例子用不泄露敏感列的假设元组或已公开的业务键。
- [ ] 优先研究 `Products`：`product_id → name,model_provider,token_amount,price,...`；候选码还含 `name` 与 `(model_provider,token_amount)`。**当前 `product_id` 不决定历史明细 `unit_price`**，不要错误地将成交快照归一回套餐现价。
- [ ] `OrderDetails`：`detail_id →` 明细属性，`(order_id,product_id)` 也是候选码；结合 `quantity,unit_price → subtotal` 和 `quantity,tokens_per_unit → total_tokens` 的计算规则讨论冗余与更新异常，避免把业务所需历史价格视为错误冗余。
- [ ] `TokenBalances`：`(user_id,model_provider)` 唯一，`remaining_tokens` 是当前快照；`UsageSummary`：`(user_id,product_id,period_type,period_start)` 唯一，额外检查同一周期的 `period_end` 是否由周期规则决定（取决于周期起点规则，不能直接假定）。
- [ ] `Inventory` / `UpstreamAccount`：`account_id` 在库存表 UNIQUE，存在状态式 `current_quota = total_quota - used_quota` 跨表冗余；它需要维护策略，但**不能仅以跨表相等式就断言某个单表不满足 3NF**。
- [ ] `Employees`、`RestockTask`：`created_by`、`assigned_to` 两角色 FK 语义不同；`Roles` 是应用层角色而非 SQL Server GRANT。异常、库存流水的 `related_type/id` 是**弱引用**，不能伪称已受 FK 保证。
- [ ] `TokenUsageLogs` 的用户、套餐、上游账号三方事件；`InventoryLog`、`ExceptionLog` 的历史事实与语义；不能仅凭“出现重复 provider 字符串”就判定需要拆出新表。
- **P1 通过条件**：14/14 有候选码、FD 来源、1NF/2NF/3NF 逐项推理和三类异常结论；争议 FD 列入“待业务确认”，不作为既定迁移前提。

### P2｜决定目标模式与无损/依赖保持

- [ ] 制作决策矩阵：每项关系或字段标记 **保留、拆分、合并、受控反规范化**；写出适用业务规则、候选目标字段、PK/UK/FK、性能/事务影响及回滚成本。不得因为“拆表越多越好”而重构。
- [ ] 如果找到不满足 3NF 的 FD：先给出消除部分/传递依赖的具体目标关系，逐步证明**无损连接**（例如利用共同属性是某个分解关系的键等条件），检查原有关键 FD 能否由新表约束独立维护；依赖不保持则写明额外事务或检测逻辑。
- [ ] 对 `Orders.total_amount/total_tokens`、`OrderDetails.subtotal/total_tokens`、`Inventory.current_quota`、`UsageSummary` 的冗余：说明保留快照/汇总的业务收益，以及谁在事务中维护、何时对账；必要时记录未来改成计算列/视图的影响，**不默认改变历史语义**。
- [ ] 对第五周待定的 **散客、同商品多明细、账号必有库存、自动补货创建人** 做决策门槛；没有用户/小组明确业务结论，不得擅自改变 NOT NULL/UNIQUE/外码或虚构“系统员工”。
- [ ] 如果现有结构符合要求且无业务批准的必要调整：选择**保留路径**，提供一份独立、与业务隔离的异常与分解小例子；迁移脚本通过前提检查并明确记录“本次无需结构变化”，而不是偷偷空跑或造新业务表。
- [ ] 如果确有必要调整：选择**实际迁移路径**，形成“旧列 → 新列/新表”的字段映射、冲突处理、NULL/重复策略、旧表保留与视图依赖迁移顺序、具体撤销/重建约束步骤。
- [ ] 更新目标 ER 源与 SVG、目标数据字典，与最终迁移后的字段及 FK 一致；沿用 `week5` 可编辑 ER → `render_er.py` 的流程，图像线尽量少交叉，基数统一用 `1..1/0..1/0..*/1..*`，多角色 FK 不合并。
- **P2 通过条件**：每项拆分/保留有决策理由、目标属性与码；理论上证明无损连接、说明依赖保持或补救方式；目标图与待迁移 DDL 映射一致。**P2 决定的迁移范围须用户批准后进入 P3**。

### P3｜编写并在副本执行 sql/migration.sql

- [ ] 头部写明适用 SQL Server、**唯一目标副本名/数据库版本**、预期源表/列/行数/约束检查、执行顺序、数据冲突停止策略、再次运行所需初始状态、失败恢复方法；不要隐式选择 master 或任何正式 v0.1 库。
- [ ] 在实迁移路径中按**依赖顺序**进行：核对备份 → 检测重复/NULL/引用冲突 → 新表创建及新字段调整 → 数据复制和必要转换 → 记录主码/候选码/FK/CHECK → 双向计数/业务键核对 → 兼容视图、权限及旧表处理。任何 DROP/重命名旧表必须有明确依据和可恢复方案，原则上先保留旧表、迁移验证通过后再由用户另行批准清理。
- [ ] **脚本要阻止不安全输入**：若数据库名、结构版本、预期约束、唯一键、检查前提不匹配，明确 `THROW` 并拒绝执行，不把部分写入看作成功。
- [ ] 按 SQL Server 实际行为处理事务边界和 DDL 操作，`TRY/CATCH` 检查 `XACT_STATE()`，记录异常，能回滚的事务回滚；无法原地回滚的情形用 P0 的可靠备份重新还原到**新隔离目标**，禁止覆盖源库。
- [ ] 校验新建 PK/UNIQUE/FK/CHECK 的**启用且受信任状态**（避免 `WITH NOCHECK` 放过旧数据）；支持数值精度、时间、状态与排序语义保持，防止静默截断/舍入。
- [ ] **保留路径**也要提供可执行、可核验的 `migration.sql`：确认目标是已还原的 v0.1 数据副本、结构符合约定、无需迁移字段，输出清晰状态，绝不空泛写“成功”。
- **P3 通过条件**：本阶段脚本仅在已授权、预先核验的**副本**上运行；所有目标约束满足；变更前后的数据与原库可恢复。禁止将“建一个空的 v1.0 库再生成样例”代替旧行迁移。

### P4｜编写 sql/regression.sql 与差异报告

- [ ] **订单明细**：比较每笔订单的明细集合、产品、数量、快照价格、Token、汇总金额；迁移后若拆表导致行数变化，按业务键重建视图再与旧查询**双向 EXCEPT** 比较，不简单要求新旧表行数一致。
- [ ] **商品销售**：按原 `paid` 状态、成交快照和原统计口径对账商品销量/收入以及无销售商品是否保留；明确不把当前 `Products.price` 误当历史成交价。
- [ ] **库存**：比较上游账号余额、阈值状态及库存流水汇总；独立核对 `total_quota-used_quota` 与 `Inventory.current_quota`；固定历史快照口径不变。
- [ ] **结构与键**：检查原业务主键/候选码映射、无重复、无孤儿、必要字段不为 NULL；全部新增约束在 sys 目录处于启用且可信状态，不能靠仅一份样例判定无损。
- [ ] **合法写入**：事务内执行符合约束的 INSERT/UPDATE，检查实际结果与 FK/派生字段/事务规则，执行后回滚并验证恢复。
- [ ] **非法写入**：重复候选码、无效 FK、负数/非法数量等反例必须失败，明确 SQL Server **预期错误号及适用约束名**；错误号不符、意外成功或数据污染都判 FAIL。
- [ ] **权限**：复核 manager/staff/customer/guest 的允许/拒绝操作，覆盖新表、兼容视图和现有基表；避免新对象默认暴露给 public 或直接绕开个人视图。对可追溯的 `EXECUTE AS` 负例按 XACT 状态先回滚再 `REVERT`。
- [ ] **业务历史规则**：依旧检测注册时间、付款到账/使用顺序、历史余额、provider 匹配、上游有效期；尽可能复用和适配原 `sql/verify.sql` 与 `tests/`，不要删除原来的检查。
- [ ] 保存每项 **原基准、预期、迁移后结果、PASS/FAIL、SQL 位置、差异原因**；失败需保留单独日志，不覆盖旧结果，也不拿“命令返回 0”代替业务断言。
- **P4 通过条件**：订单明细/销售/库存语义双向核对一致；唯一性与外码受保护；合法操作成功、非法操作被**预期原因**拒绝；角色权限无扩大；合理表数变化有解释，原始 v0.1 库保持不变。

| `OrderDetails` 明细 | `detail_id PK`，`(order_id,product_id) UNIQUE`，价格/Token 快照和存储小计 | 两类候选码都要检查 2NF；旧订单价格不能由商品现价回算；小计属于可保留的冗余还是迁移对象 |
| `Orders` 总金额/总 Token | 存储并与明细总量对账 | 是受控反规范化还是拆分后计算；交易历史口径不变 |
| `Products` 套餐 | `product_id` 与 `name`、`(model_provider,token_amount)` 候选码 | 确认潜在非码 FD；不凭提供商字符串重复就添加 Provider 父表 |
| `Inventory` / `UpstreamAccount` | 库存一账号至多一行；`current_quota` 与总/已用配额有关 | 讨论快照一致性与维护成本，不把跨表一致性直接等同单表范式问题 |
| `TokenBalances` / `UsageSummary` | 联合 UNIQUE、历史消费与周期汇总 | 综合检查所有候选码、period 定义与汇总冗余；区分业务派生/物理 FD |
| `InventoryLog` / `ExceptionLog` | `reference_type/id` 等弱引用没有真正 FK | 迁移是否类型化取决于目标业务语义，不能直接建“万能 FK” |
| `RestockTask` | `created_by` 非空、`assigned_to` 可空 | 两条 FK 不合并；自动补货主体由业务决定 |
| `Roles` 与数据库角色 | 应用角色表与 SQL Server 的角色不同 | 表规范化分析与数据库 GRANT 验收分开，不因重构扩大权限 |
