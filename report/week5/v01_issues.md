# 第五周 v0.1 设计问题、保留项与第六周候选改进

状态：**已完成结构审查与现场只读验证；未执行迁移**。任务来源：《第五周任务讲解.docx》第 2—3 页；适用于 2026-10-10 的 `DB_lab` 正式 v0.1。以下“待确认”不等于已经发现必然设计错误。

## 一、问题清单

| ID / 判定 | 问题与业务证据 | 当前技术证据 | 影响/风险 | 保留/第六周候选处理 | 人工确认 |
|---|---|---|---|---|---|
| I01 / 约束缺口 | **订单至少一条明细**是销售业务必需；无明细订单不构成完整购买 | `OrderDetails.order_id NOT NULL` + `FK_OrderDetails_Orders` 只能约束明细→订单；现场 0 张无明细订单 | 单独插入订单头可能留下空订单或不准确总额 | v0.1 保留，六周设计订单创建事务/延迟提交验证、应用入口约束；不可误称 FK 已保证 | 业务规则待复核 |
| I02 / 需求需决策 | **一单同商品出现多条明细**是否允许？教学提示明确“不要默认只能出现一次” | `UQ_OrderDetails_order_product` 阻止重复行；`quantity` 可表示同商品多件，现场 184 行 / 100 单，68 单有多行 | 若未来需要不同折扣/分批/不同价格的同商品明细，现约束会拒绝 | 若业务规定合并同商品，则保留 UNIQUE 并写明；否则六周先设计 detail_id 独立唯一并迁移兼容逻辑 | **必须讨论** |
| I03 / 功能范围差异 | **真正无账户散客购买**：任务要求解释会员或散客情况 | `Orders.user_id INT NOT NULL` 且 `FK_Orders_Users`；所有现场订单均有用户 | 无法原样记录 `user_id=NULL` 散客订单，演示不可称支持 | 若散客需要临时用户记录，保持 FK、增加客群定义；若允许匿名订单，六周设计可空关联与散客识别字段、权责校验 | **必须讨论** |
| I04 / 参与缺口 | **每个上游账号是否必须有库存？** 经营上通常希望可查询额度 | `Inventory.account_id UNIQUE NOT NULL` + FK 使账号最多一个库存行，但允许没有；当前现场 0 个缺库存账号 | 账号可能被创建后暂时不能查到库存，额度不可见 | 若业务要求 1..1，六周考虑同事务创建、唯一 FK 加过程保障；本周保留现状 | 需运营确认 |
| I05 / 跨表一致性 | 产品和上游账号 provider 必须匹配，调用只允许在有效期内 | `TokenUsageLogs.product_id/account_id` 是独立 FK；不保证 provider 相等。`sql/verify.sql` VFY12 查历史，现场不匹配为 0 | 错配消费/过期账号消费只在回归中暴露，不能保证每次写入被立即拒绝 | 保留两个明确实体；六周研究 provider 关联方案，后续事务层确保校验 | 推荐保留实体划分 |
| I06 / 跨表汇总 | 订单总额与明细汇总、库存与上游额度、库存流水保持一致 | `sql/verify.sql` VFY 对账；本周现场 `header_detail_mismatch=0`、`inventory_quota_mismatches=0` | 不同步更新会产生阶段性或永久矛盾 | 第六周先决定受控冗余是否保留；应用阶段统一事务更新，不把非实时验收当成即时 DB 约束 | 需确认更新策略 |
| I07 / 职责冲突风险 | 自动补货任务应能由系统触发，而不是强制人工创建 | `RestockTask.created_by INT NOT NULL` FK；`assigned_to` 可空；现场 3 个任务未指派 | 自动创建任务必须借用专用“系统员工”或修改模型 | 六周讨论系统主体设计、可空/来源字段；不要盲目删除 NOT NULL | 待运营确认 |
| I08 / 弱引用 | 流水与异常需要关联真实业务对象，便于追溯原因 | `InventoryLog.reference_type/reference_id`、`ExceptionLog.related_table/related_id` 无指向目标对象的 FK | 可能引用不存在/类型不一致的目标对象；删除目标后无法严格追溯 | 六周评估专门关联表、类型化 FK 或可追踪的独立事件标识 | 需明确引用类型 |
| I09 / 历史余额 | 会员任何时点不应先消费后到账 | `TokenBalances.remaining_tokens >= 0` 仅约束当前行；`verify.sql` VFY13 逐事件核对 | 当前余额大于 0 仍可能隐藏历史负债 | 保留余额快照与原始消费日志，后续事务化支付/调用；测试同秒先到账规则 | 必须保留事件语义 |
| I10 / 应用角色与数据库角色不同 | 角色业务关系应该可解释；员工角色和数据库 GRANT 不是同一实体 | `Roles.role_name` 有 `admin/staff/customer` CHECK；`hub_manager/hub_staff/hub_customer/hub_guest` 是独立 SQL Server ROLE | 若把 `Roles` 当数据库登录授权表会误解权限覆盖；会员无 FK 到 `Roles` | 保留职责区分，文档列明映射与用户可操作范围；后续应用认证阶段再决定是否统一角色模型 | 需团队确认 |

### 证据解释规则

- **SQL 可以立即保证**：FK、NOT NULL、UNIQUE、同表 CHECK；引用对象存在与每个子行对应父行数量可由结构推断。
- **数据库当时确实满足**：`readonly_validation.log` 的样例计数和零异常结果，属于 **2026-10-10 的单库现状**，不是数据库始终强制、也不代表所有库。
- **业务愿望但结构没有保证**：散客是否允许、订单必须有明细、自动创建人、弱引用目标存在等。不要在 ER 实线或“已通过”中混同这三层。

## 二、应保留的合理设计（并写出代价）

| ID | 保留设计 | 理由 | 已知代价 / 管控 |
|---|---|---|---|
| K01 | 订单头与 `OrderDetails` 分离 | 一次订单能够包含多商品，每个明细能保存成交快照；当前 68 张订单有多条明细 | 汇总字段需要跨表对账；同商品唯一性须业务确认 |
| K02 | `OrderDetails.unit_price/tokens_per_unit` 快照 | 套餐价格和档位可变化，历史已购记录不应重算 | 与 `Products` 现价不同不应判为错误 |
| K03 | `UpstreamAccount` 与 `Inventory` 分离 | 上游账号身份与当前额度状态含义不同，产品套餐不等于上游账号库存 | 一账号一库存的覆盖率需要控制 |
| K04 | `TokenBalances` 使用 (`user_id`,`model_provider`) 唯一 | 不同 provider 独立余额，避免混扣 | provider 是字符枚举，缺少统一父实体 |
| K05 | 独立 `TokenUsageLogs`、`InventoryLog` | 消费/额度改变有历史轨迹，能核对当前状态 | 日志与快照需要事务保持一致 |
| K06 | `UsageSummary` 单独汇总表 | 支持日/周/月用量查询，减少高频全量聚合 | 可能与事件明细不同步，需周期与来源校验 |
| K07 | 复杂规则由单独 `verify.sql` 检测 | 能发现最终余额正常但历史有问题等跨表异常 | 回归检查不代替写入时约束，应用阶段需事务 |

## 三、第六周迁移准备顺序（本周不执行）

1. 先由小组在 I02、I03、I04、I07 四个分歧中确定明确业务语义；生成冻结后的 v0.1 ER 图。
2. 识别可能的函数依赖与异常：`OrderDetails` 复合唯一选择、`TokenBalances` provider 维度、`Orders`/ `Inventory` 跨表冗余、弱引用合法性。
3. 决定是否需要结构拆分/约束调整，再单独制定 `migration.sql` 的前置条件、迁移顺序、回滚与回归用例；**不要在第五周直接迁移**。
4. 保留旧表、历史数据、结果签名的复现依据；只有明确批准后才实施迁移，绝不默默改 v0.1。
