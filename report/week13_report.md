# 第13周：锁、隔离与死锁

实验基于从空库构建的 `TokenHubDB_v11_WebW13Run03`，SQL Server 版本 **17.0.1000.7**。连接 A（SPID 97）和 B（SPID 98）的初始隔离级别均为 READ COMMITTED，RCSI 关闭；观察连接 SPID 99。未修改 RCSI。证据含时间、步骤、查询结果、等待资源、锁模式和状态，见[原始并发记录](../result/week13/WebW13Run03/concurrency.jsonl)及[证据索引](../result/week13/WebW13Run03/README.md)。

| 实验 | 关键观察 | 最终状态 |
|---|---|---|
| 同行写等待 | A 将 P 从 10 更新为 8 并持有 X 锁；B 对同一键请求 X，出现 `LCK_M_X`。 | A 提交时 P=13、订单 paid；A 回滚时 P=15、订单 pending。两轮补货均入库 +5。 |
| RU 与 RC | A 临时补货使 P=15。RU 直接读到 15；A 回滚后 P=10。普通 RC 和锁提示 RC 均观察到 `LCK_M_S`，A 回滚后读到 10。 | P=10，补货仍 pending。本次未开启 RCSI；开启时普通 RC 的行为由行版本读取规则解释，未在本批次实测。 |
| RC 与 RR | RC 事务第一次读 10，B 入库提交后第二次读 15。RR 持有 P 的 S 锁，B 的 X 请求等待，A 第二次仍读 10。 | RR 的 A 提交后 B 才入库，P=15。RR 保护已经读取的键，本实验不检验是否存在幻读。 |
| 反序死锁 | A 持 P 的 X、等待 Q；B 持 Q 的 X，再请求 P。B 较低死锁优先级，收到 1205。捕获时 `XACT_STATE()=-1`、事务计数 1，清理后计数 0。 | B 的 Q 增量未保留，补货 pending；A 提交后 P=8、Q=6。 |
| 同序更新 | A、B 都按商品主键 1→2；B 先在 P 上等待，没有先持有 Q。 | 本轮两边提交，无 1205；P=13、Q=11。 |

锁记录把两个键映射到同一个 `w13lab.Stock` 索引资源：P 为 `(8194443284a0)`，Q 为 `(61a06abd401c)`。键值对应关系由每一步按主键更新的 SQL 确定。死锁中，A 请求 Q 时的 DMV 快照列出 A 持有 P、A 等待 Q 和 B 持有 Q；B 下一步请求 P，再由 1205 和最终状态核对失败事务。循环可表示为 `A → Q（B 持有）→ B → P（A 持有）→ A`。同序重放只有 `B → P（A 持有）`。

## 业务事务的验证

项目不在支付时直接减少物理库存，而是发放 Token 批次占用可售余量；后续调用才扣物理库存。因此按商品主键排序只用于 P/Q 模型，实际事务通过 `w12.usp_LockInventoryProvider` 共享逻辑锁，订单按供应商名称升序取锁，补货取得其单一供应商的锁。锁属于事务，外层事务结束才释放。成功取得入口锁后仍使用原有行锁、容量检查、流水和审计。超过入口锁的 15 秒等待上限返回业务冲突；没有自动重试。

实测同一供应商 `Other` 上，A 的订单事务持有 `TokenHub.Inventory.Other` 的 APPLICATION X 锁，B 调用补货事务等待。A 回滚后 B 完成入库；为保留竞购基准，B 再回滚其外层事务，补货单回到 pending。

随后两个会话各结算 P×6。实际商品编号 98，每份对应 9,991,024 上游额度，初始可售 10 份。第 154 号订单成功变成 paid，发放 550,218 Token 和一个批次；第 155 号订单等候同一入口锁，A 提交后返回 53132，仍为 pending、未产生余额或批次。物理可用额度仍为 101,417,013，扣除待消耗额度 61,452,917 后，可售余量为 39,964,096，即 **4 份**。

限制：固定取锁顺序消除了这次重放所构造的反向依赖，不能保证全系统不发生死锁。其它写入路径仍执行各自数据库规则；本轮未扩展隔离级别范围，也未重新验收人工浏览器动线或普通 Windows 运行账户。第10—12周同一套全量回归已在本批次复跑。
