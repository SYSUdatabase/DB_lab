## 层级递归查询

样例层级为根“全部Token套餐”(1)，子节点“文本对话模型”(2)与另一条分支“多模态与其他”(3)，孙节点为四个供应商分类(4—7)，OpenAI 分类下再分小容量(8)和大容量(9)两个叶子；现有 10 个商品按供应商和容量挂到叶子分类。

递归 CTE 的锚点只取指定编号，层级为 0；递归部分用 `子分类.parent_id = 上一层.category_id` 连接，层级加 1、路径追加本节点；没有更深的子分类时终止。路径列在两部分都转换为 `NVARCHAR(400)`。外键只保证父级存在，不能阻止成环，所以另加防环触发器；查询本身也排除路径中已出现的编号并限制 32 层，语句带 `OPTION (MAXRECURSION 32)`。

| 起点 | 结果（原始输出见 [recursive_query.log](../result/week12/WebXY1124D/recursive_query.log)） |
|---|---|
| 根节点 1 | 9 行，层级 0—3，例如 `/1/2/4/8/`：全部Token套餐 > 文本对话模型 > OpenAI套餐 > OpenAI小容量（≤100K） |
| 中间节点 2 | 5 行：2、4、8、9、5，层级 0—2 |
| 叶子节点 8 | 1 行，只有自身 |
| 不存在的编号 999 | 0 行，脚本提示“分类不存在” |

对照样例关系，各节点的父级、层级和路径均正确。脚本最后用函数列出分类 2 及其后代下的 7 个商品。

安装时先按供应商和容量为已有商品建立 `w12.ProductCategoryAssignments` 初始映射。之后由 `dbo.trg_W12_ProductCategoryAssignments` 在 `dbo.Products` 的 INSERT、UPDATE 后自动维护：OpenAI 按 `token_amount <= 100000` 分到分类 8，否则分到分类 9；Claude、Gemini、Other 分别分到分类 5、6、7。商品修改供应商或容量时，映射随之调整；商品删除成功时，`product_id` 外键的 `ON DELETE CASCADE` 自动清除映射。该触发器位于数据库层，Web 商品维护与直接 SQL 写入共用同一逻辑。递归函数本身不变，查询通过分类映射表关联商品即可得到最新归属。已有订单或调用历史的商品仍受历史保护与外键约束，不能通过修改分类映射绕过。

## 订单完成事务

项目组确定数据库状态值仍为 `paid`，报告与测试记录统一写作“已完成（paid）”，并保持原有扣减时机：上游库存在顾客模拟调用时按实际用量扣减。原因是本项目出售的是 Token 套餐，顾客付款后余额才可用，上游账号的消耗发生在调用时；若在完成订单时就扣上游库存，调用时还要再扣一次，或者要改写已有的 FIFO 批次、调用和退款账务。因此完成事务不扣上游库存，而是做三件事：核对可售余量、按供应商把 Token 记入顾客余额、逐明细发放 Token 批次。“一张订单只记一次余额”由状态条件更新 `WHERE status='pending'` 加受影响行数检查保证。

`w12.usp_CompleteOrder(@order_id)` 在 SERIALIZABLE 隔离级别下依次执行：锁定订单行并按状态给出结果（不存在 53123，已完成 53131，非待支付 53123）；检查买家、明细、商品与数量、金额与 Token 合计、第10周折扣快照；按商品汇总需求量，再按供应商汇总；先锁本顾客的余额行，再按“份数 × 每份上游消耗”核对可售余量（不足 53132，口径见[第11周报告](week11_report.md)），加锁顺序与模拟调用一致；记入余额；把订单改为 paid（触发第11周完成规则触发器再核对一次）；发放批次；提交。

事务边界与调用关系：

```text
Web  app.[Execute] 'orders.pay'          外层事务，入口统一提交或回滚
  └─ dbo.usp_W6_PayPendingOrder           原名薄封装，不另开事务逻辑
       └─ w12.usp_CompleteOrder            检查、记余额、改状态、发批次
            └─ UPDATE dbo.Orders → dbo.trg_W11_OrderCompletionRules 等触发器（同一事务）
```

嵌套时由 `app.[Execute]` 这一层负责提交：里层过程的 COMMIT 只把 `@@TRANCOUNT` 减一；里层出错时 CATCH 中的 ROLLBACK 回滚整个外层事务（`@@TRANCOUNT` 归 0）后重新抛出原错误，外层 CATCH 看到 `XACT_STATE()=0` 不再回滚，网页收到原错误号，不附带 266 号事务计数错误。直接用 SQL 在自己开的事务里调用时同理：里层出错会连同调用者此前的改动一起回滚。

Web 入口在调用事务过程之前先按订单或补货单状态检查：已完成的订单再次“模拟支付”、已入库的补货单再次“完成补货”，由 `app.[Execute]` 返回 55009，页面统一提示“当前状态、余额或可用额度不满足操作条件”（HTTP 409），数据不变；53131、53311 只在直接 SQL 调用事务过程时出现。

## 补货入库事务

补货单沿用 `dbo.RestockTask`：员工为某个上游账号填写计划补货量，入库时填写实际到货量；补货单编号、账号（对应供应商的商品）和数量的对应关系保存在这张表里，第四阶段可把人工数量换成预测结果。`w12.usp_ReceiveRestock(@task_id, @actual_amount)` 先拒绝非正数量（53303），再锁定补货单并区分不存在（53310）、已入库（53311）、已关闭（53312）；检查账号可补货、该供应商有在售商品、额度不溢出、库存与总额度一致；随后增加总额度和库存（第11周审计触发器记录 increase）、写入补货流水、把单据改为 completed 并填写实际量与入库时间，最后核对库存等于总额度减已用后提交。同一单据再次入库返回 53311（经 Web 为 55009），不再增加库存。调用关系与订单相同：`app.[Execute] 'restocks.complete'` → `dbo.usp_W6_RestockAccount` → `w12.usp_ReceiveRestock`。

故障点用会话上下文 `w12.fail_point` 触发，只在测试连接中设置；失败发生在已经写入部分数据之后，用来证明回滚有效，而不是在执行前拒绝参数。故障点保留在正式过程中：任何连接（包括受限运行身份）都可以给自己的会话设置这个值，效果只是让本连接这一次调用报错并整体回滚，不能改动数据；会话上下文按连接隔离，Web 每个请求新开连接且关闭连接池，因此也影响不到其他请求。

讲义要求每次测试前重置数据。本脚本不重置整库，而是在每个用例前新建自己的商品、订单或补货单并记录初始值，用前后差值判断结果，这样不需要删除或回退已有业务数据，脚本可在同一库上重复运行（复查时在临时库 WebXY1123V 上连续运行两次，均为 12/12）。用例之间有依赖：T2 使用 T1 已完成的订单，T4 使用 T3 回滚后的订单，R2 使用 R1 的补货单，R4、R5 使用 R3 回滚后的补货单；全部订单用例共用顾客 `web_customer` 与 Other 供应商的可售余量，补货用例共用同一个测试账号。

覆盖范围：T5 核对订单状态、完成时间、余额与批次；R2 核对库存、总额度、流水、审计及补货单的状态、实际量和入库时间；R4 核对库存、总额度、流水、审计与单据状态；R6 覆盖 53312（补货单已关闭）。53313（供应商无商品）没有可执行用例：Products 与 UpstreamAccount 的供应商取值都受 CHECK 限制为 OpenAI、Claude、Gemini、Other，被订单引用的商品不能改供应商（`trg_W6_ProductsHistory`）也不能删除，样例库中四个供应商都有被引用的商品，因此该检查在本库不会触发；R7 核对这一前提，53313 作为防御性检查保留。

## 并发核对

讲义的并发实验在第13周进行；本周复查时先做了一次压测：6 个顾客各 20 张待完成订单（同一 Other 供应商的商品），6 个线程同时完成，直接调用 `w12.usp_CompleteOrder` 与经 `app.[Execute]` 的“模拟支付”各一轮。最初的实现在核对可售余量时以 SERIALIZABLE 读取所有已售批次，两个事务各自持有这段范围的共享锁，随后都要插入新批次，互相等待形成死锁（1205），被选为牺牲者的付款失败，页面提示“操作发生冲突”。数据保持一致，没有超卖。修改为在核对可售余量之前先以 `UPDLOCK,HOLDLOCK` 锁住本单涉及供应商的上游账号行，同一供应商的订单完成在此排队。新库 WebXY1124A 上的结果（[压测日志](../result/week12/WebXY1124A/stress.log)）：

| 实现 | 直接 SQL（120 单） | 经 Web 入口（120 单） |
|---|---|---|
| 修改前 | 成功 36，死锁 1205 共 84 | 成功 37，死锁 1205 共 83 |
| 修改后 | 120 全部成功 | 120 全部成功 |

两轮结束后库存与“总额度−已用”、余额与未消费批次合计均无不一致。同一订单被两个连接同时完成、同一补货单被同时入库，各 10 轮均为一次成功、一次被拒（直接 SQL 为 53131、53311，经 Web 为 55009），批次只发一次、库存只加一次。锁等待与隔离级别的完整实验留到第13周。
